# Windows checks before contacting IT support

**Editorial status:** Draft for UX, accessibility, bilingual, and technical review. Not yet published.

**Planned route:** `/windows-checks-before-it-support.html`

**Audience:** A person using a Windows workstation who needs to describe a problem and perform only safe first checks.

## Prepare a clearer, safer support request

When a Windows computer stops supporting the task you need to complete, it is tempting to try many fixes at once. That can hide the original symptom or create a second problem.

Start by identifying the failed task, protecting your work, and recording what you can see. The goal is not to repair every problem yourself. It is to separate simple conditions from issues that need an authorized technician.

This guide covers reversible checks that do not require administrator access. Follow your organization’s support policy when it differs from this guide.

## First decide whether you should stop

Do not continue troubleshooting when:

- the device may be physically unsafe;
- files appear to be disappearing, encrypted, or damaged;
- you see an unexpected request for a password, payment, remote access, or security code;
- a warning tells you to call a telephone number shown in a pop-up;
- the action would require opening the device, changing firmware, bypassing security, or using an administrator account;
- the computer contains sensitive organizational information and you are unsure what may be shared.

Disconnect from the immediate activity when it is safe to do so and contact the approved support or security channel. Do not call a number displayed in an alarming pop-up. Microsoft states that genuine Microsoft error and warning messages do not include telephone numbers.

## 1. Describe the task that failed

Begin with the user task, not a diagnosis.

Instead of writing “the computer is broken,” record:

- what you were trying to do;
- the application, device, or website involved;
- what you expected to happen;
- what happened instead;
- whether the problem occurs every time or only sometimes;
- when you first noticed it;
- whether another person or device has the same problem.

Example:

> At 09:20, I tried to print a two-page PDF from the office workstation. The document stayed in the print queue and no page came out. Printing worked yesterday. Another user can print to the same device.

This description gives the technician a useful starting point without claiming that the printer, network, or application is already known to be the cause.

## 2. Protect open work

Before restarting or closing an application:

- save any document that still responds;
- note which files and applications are open;
- avoid forcing a shutdown while a file is being saved or updated;
- do not continue if the device may be physically unsafe or data appears at risk.

If the application is frozen, record its name and the last action you completed. An authorized technician can decide whether a forced close or restart is appropriate.

## 3. Check simple visible conditions

Only check what you can observe without changing protected settings.

### Device and power

- Is the computer, monitor, printer, or accessory powered on?
- Is a cable visibly loose or disconnected?
- Does the screen show a message, indicator, or unusual state?
- Is the expected keyboard, mouse, headset, or removable device connected?

Do not open equipment or repeatedly reconnect damaged components.

### Network

- Check the network indicator in Windows.
- If you use Ethernet, confirm that the cable is securely connected without moving other network equipment.
- Check whether another approved website or service works.
- If permitted, determine whether another device on the same network has the same problem.

This comparison helps distinguish one-computer symptoms from a wider service problem. It does not prove the final cause.

### Application or website

- Confirm the exact application or browser tab affected.
- Check whether the issue affects one file or every file you are permitted to test.
- Read the full message before dismissing it.
- Avoid installing a “repair” tool suggested by an advertisement or unexpected pop-up.

## 4. Consider a normal restart

A normal Windows restart can clear a temporary state, but it should not be the first response when unsaved work or an active update may be at risk.

If your work is saved, the device is responsive, and local policy permits it, use **Start → Power → Restart**. Do not hold the power button unless an authorized support process tells you to do so.

After the restart, repeat only the original safe task once. Record whether the result changed. Repeating a failing action many times can create duplicate print jobs, messages, or transactions.

## 5. Record recent changes

Think about what changed before the problem appeared:

- a Windows or application update;
- a restart or power interruption;
- a new application, peripheral, or cable;
- a password or account change;
- a move to another desk, room, or network;
- a change made by another authorized person;
- no known change.

Do not remove the update, driver, application, or account yourself merely because it appears in the timeline. Timing is evidence to investigate, not proof of cause.

## 6. Capture useful information safely

Record the exact wording of an error when possible. A screenshot may help, but review it before sharing.

Remove or hide information that support does not need, including:

- passwords and security codes;
- personal or financial information;
- private messages;
- confidential document contents;
- unnecessary account, device, or organization identifiers.

Never send a password in a ticket, email, chat, or screenshot. Use only the support channel approved by the organization responsible for the device.

## 7. Separate the symptom area

Choose the closest description. Do not treat it as a final diagnosis.

| Symptom area | Useful observation |
| --- | --- |
| Startup or sign-in | Where the process stops and the exact message shown |
| One application | Application name, affected task, and whether another safe file works |
| Network or website | Network indicator, affected service, and whether another approved service works |
| Printing | Printer selected, queue state, and whether another user is affected |
| Sound or peripheral | Device connected, visible status, and whether Windows detects it |
| Performance | Task that is slow, when it started, and whether the slowdown is constant |

This classification helps the support team route the request and choose the next authorized checks.

## 8. Prepare the support request

Use this concise structure:

### Task and impact

What task cannot be completed? Who or what work is affected?

### Time and frequency

When did it start? Is it constant or intermittent?

### Exact symptom

What appears on the screen or device? Include the exact error text after removing private information.

### Recent change

What changed shortly before the issue, or is there no known change?

### Safe checks completed

List only what you actually checked and the result of each check.

### Contact and availability

State how the approved support team can reach you and when the device can be examined. Do not include passwords or unrelated personal information.

## What happens next

The technician may ask follow-up questions before changing anything. A structured request helps them reproduce the problem, protect data, choose authorized tools, validate the original task, and document the outcome.
